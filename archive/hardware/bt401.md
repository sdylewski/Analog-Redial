# BT401 (DFRobot DFR0781) Bluetooth module: firmware and bring-up

> **Status (2026-10-27): working on a v5 board** (ACEBE6C21C04, hand-wired to J2, no adapter board yet).
> Pairing, music, incoming calls ringing the bell, dial-out (9 + number) and call audio both ways all work;
> the user rates call delay as minimal and prefers it to the BM64. Still to test: the items under
> [Still open](#still-open).

Wiring, pin table and footprint notes: `Bluetooth/DFR0781_BT401/BT401_NOTES.md`.
Sources: `Bluetooth/DFR0781_BT401/` (datasheet, schematic, a copy of
`DFRobot/DFRobot_BT401`, MIT).

## What is in the firmware

| File | What it does |
|---|---|
| `firmware/components/bt_companion/bt401_proto.[ch]` | Pure C: builds `AT+...` lines, splits the reply stream into lines, decodes them, keeps the link/call state. Host-tested. |
| `firmware/components/bt_companion/bt401.[ch]` | The UART and the background task: polls `AT+TS`, folds replies into the state, call control, dialling, DAC on/off, bring-up helpers. |
| `bt_companion.c` | Dispatches to `bt401_*` when Settings → Hardware says **BT401 module fitted** (`BOARD_BT_BT401`). |
| `firmware/test/host/test_bt401_proto.c` | Checks the parser and state machine against the datasheet's example lines. Run with `firmware/test/host/run.sh`. |

Console commands (bringup.c): `bt401_probe`, `bt401_at <cmd> [listen_ms]`, `bt401_state`,
`bt401_dial <number>`, `bt401_selftest`. `hwcfg bt bt401` and
`first_setup.py --bt-module bt401` choose the module.

The settings value for "BT401" is the same number the removed BK3266 option
used, so a board that had BK3266 saved now reads as BT401.

## Protocol in one screen

Text, 115200 8N1, lines end in CRLF. Host sends `AT+<cmd>[param]`; the module
answers `OK`, `ER+<n>`, or a `<XX>+<value>` line.

| Do | Send | Reply |
|---|---|---|
| status | `AT+TS` | `TS+00` waiting · `01` connected, idle · `02` music · `03` ringing (in or out) · `04` in a call |
| caller / dialled number | `AT+TT` | `TT+<number>` (repeated by the module every 2 s) |
| answer / hang up / reject | `AT+BA04` / `BA03` / `BA02` | `OK` |
| dial | `AT+BT<number>` | `OK`, then `TS+03`, `TS+04` |
| pairing (discoverable) | `AT+BA06` | `OK` |
| drop the phone | `AT+BA01` | `OK` |
| enable calls | `AT+B201` | `OK` (stored by the module) |
| DAC off / on | `AT+CS00` / `AT+CS01` | `OK`; off = output high-impedance |
| set name | `AT+BD<name>` (max 32 bytes), then `AT+CZ` (reset) | `OK`; stored by the module |
| own name / address | `AT+TD` / `AT+TA` | `TD+BT401-AUDIO-V31` / `TA+AD89434D5A13` (real module) |

At power-up the module volunteers a burst of lines (`TL+..`, `T1+..`..`T9+..`, `TE+..`, `TD+..`, `TA+..`,
`TM+BT401-BLE`, `TB+..`, `TR+0123456789`), and after `AT+CZ` also `QN+..`, `QK+..`, `QG+..`, `Q1+..`, `C5+..`.
It also volunteers `TS+..` on a change; the driver still polls `AT+TS` every 1.5 s to catch a missed one.

How the driver reads it: `TS+03` is **outgoing** if the driver just sent a dial
command, otherwise **incoming**; `TS+04` is active; `TS+01`/`TS+02`/`TS+00`
end any call. The phone's own name isn't available from the module, so the web
UI shows no paired name.

The driver keeps the module's DAC off (`AT+CS00`) unless there is Bluetooth audio (`TS+02` music, or a call), and
turns it back on (`AT+CS01`) when it stops. An idle DAC is a low-impedance node and, through R16, it pulls line 0's
earpiece input down (see the bench log below).

## Still open

1. **Call end:** hanging up on the handset, and the far end hanging up: both should end the call promptly.
2. **Caller ID:** when `TT+` first appears, and what a withheld number gives.
3. **Unanswered and declined calls:** the bell must stop when the caller gives up or the call is declined on the mobile.
4. **DAC switching:** whether the first word of a call or song is clipped, or pops, when the DAC turns on.
5. **Far end's view:** mic level and echo as heard by the other party.
6. **Reconnect:** after walking out of range and back, and after a board power cycle.
7. **Volume:** `AT+QA` reply wasn't seen in the log; `AT+CA` (0-30) is the module's own volume if ever needed.
8. **Device name:** the firmware doesn't set it yet; this board was renamed by hand to "Phone.AnalogRedial"
   (`AT+BDPhone.AnalogRedial`, `AT+CZ`). Idea in `archive/FEATURE_IDEAS.md`.

## Log

**2026-10-27, first module (board ACEBE6C21C04, SMD5 v5, genuine DevKit, 1 line).** Answered at once at
115200 (`TS`, `TD`, `TA`), default name "BT401-AUDIO-V31". The codec was missing at first only because the
DevKit headers weren't soldered. Paired a phone, music played through the handset, an incoming call rang the
bell, and dialling out with 9 + number worked with good audio both ways. Renamed the module with `AT+BD`.

### Line 0 earpiece loaded by the BT401 DAC

Line 0 was very quiet in the earpiece and the audio-level check failed ("no test tone came back"). Unplugging
the BT401's DACL wire (J2.7) made it loud again. The codec reaches the SLIC's VIN through a 10 nF coupling cap
(about 16 kohm at 1 kHz); the module's DAC, through C23 1 uF and R16 1 kohm, is a low-impedance path from the
same node and shunts nearly all of it. A larger series resistor helps the dial tone but makes Bluetooth audio
much quieter (4.7 kohm was already too quiet). Turning the DAC off when idle fixes it with no added resistor.

The level check plays a tone out the codec and measures what returns from the SLIC's VOUT, so it reflects the level
reaching VIN (no scope needed). Console: `selftest`, then `selftest action level0`, on-hook, level 30.

| BT401 DACL wire on J2.7 | Total in series (R16 + added) | Returned tone | Distortion | Notes |
|---|---|---|---|---|
| unplugged | n/a | -26.2 dBFS (three runs: -26.2, -26.2, -26.0) | 0.46-0.96 % | reference; dial tone loudest |
| fitted | 1 kohm (R16 only) | no tone | n/a | "line 0 unpowered or Vout open", very dim |
| fitted | 23 kohm (22 kohm added) | -33.1 dBFS | 0.72 % | about 7 dB below the reference |
| fitted | 48 kohm (47 kohm added) | -29.8 dBFS (two runs) | 0.55-0.75 % | about 3.6 dB below |
| fitted | 101 kohm (100 kohm added) | -27.8 dBFS (three runs) | 0.47-1.4 % | about 1.6 dB below; Bluetooth music really quiet |
| fitted, DAC on (`AT+CS01`) | 5.7 kohm (4.7 kohm added) | -29.7 dBFS | 1.0-2.8 % | Bluetooth music much dimmer than at 1 kohm |
| fitted, DAC off (`AT+CS00`) | 5.7 kohm (4.7 kohm added) | -26.2 dBFS | 0.6 % | same as the reference |
| fitted, DAC off (firmware, idle) | 1 kohm (R16 only) | -26.2 dBFS (two runs) | 0.4-1.1 % | same as the reference; music at full level |

**Fix:** no added resistor; the driver switches the DAC (above). While the DAC is on the codec is loaded again, but
then the line is carrying Bluetooth audio anyway.

### Supply current (3.3 V from J2.1, 2026-10-28)

Measured in the module's VCC lead (module firmware `AT+VER2.3-20201230`):

| State | Current |
|---|---|
| Phone connected, idle (`TS+01`) | 13 mA |
| Phone connected, music streaming | 21 mA |
| No phone (forgotten), searching (`TS+00`) | 30-32 mA |
| No phone, idle mode `AT+CM08` (Bluetooth still in the background) | 32 mA, still visible to phones |
| No phone, BLE off (`AT+B400`, stored, after `AT+CZ`) | 31 mA: BLE costs nothing measurable |
| No phone, `AT+CG00` (no background Bluetooth, stored) + `AT+CZ` + `AT+CM08` | **7 mA** |

`AT+BA07` (stop being discoverable) answers `ER+4` in both idle and Bluetooth mode. So the only real "off" is
`AT+CG00` once (stored) plus `AT+CM08`, and `AT+CM01` to come back. This module is now left with `CG00` and BLE off
(`B400`); `B401` / `CG01` undo them.
