# BK3266 Bluetooth module — bring-up journal

> **Status (2026-10-09): firmware written, nothing tested on a real module.**
> The BK3266 daughter board was sent to fab with the SMD5 main board and
> hasn't been mated to anything yet. Everything below marked **UNVERIFIED**
> comes from the vendor's documents. When a real module is on the bench,
> work through [the bring-up sequence](#bring-up-sequence) and write what
> actually happened into [the log](#log) and the unverified list.

A cheap (~$2–3) alternative to the BM64 (~$8–12) for the same job: pair a
phone, and make the rotary phone its handset. Same 8-pin header (`J2` on
SMD5), same analog audio path, different UART protocol — and **it can't
dial out**.

## What the daughter board is

`Bluetooth/BK3266_board_v1/` — BK3266SR module (40-pin, `U1`), an 8-pin
female socket `J1` that mates with the main board's `J2`, a 6-pin
diagnostic header `J2` (unpopulated), and a few resistors and an LED.

| Ref | What | Notes |
|--|--|--|
| U1 | BK3266SR module | VBAT pin 37, UART pins 10/11, WAKEUP pin 7 |
| J1 | 1×8 female socket | The connection to the main board, see below |
| J2 | 1×6 male header | Probe/tweezer access: S/R, STAT, GND, MODE, COM, PP/CALL |
| R1 | 1 kΩ | LED current (module pin 14 → D2 → R1 → GND) |
| R2 | 1 kΩ | Series on STAT (pin 19) → J2.2 |
| R3 | 1 kΩ | Series on S/R → J2.1. On pin 22 (the duplicate S/R pad); pin 13 is unconnected |
| R4 | 10 kΩ | +3.3 V → J2.5 "COM" (current-limited button supply) |
| D2 | 5 mm LED | Module pin 14 (GPIO8) status LED |

Left unconnected on purpose: both `AUDIOLN`/`AUDIORN` and the right channel
(`AUDIORP`), `AUX_L/R`, `VBUS`, `V2MICBIAS`, the SD pins, `Mute`, `Next/Vol+`,
`Prev/Vol-`, and the two 3 V outputs. `AGND` (pin 40) is tied to GND with the
other grounds.

### J2 diagnostic header

| Pin | Net | Module pin | Use |
|--|--|--|--|
| 1 | S/R | 22 (via 1 kΩ) | Output: high = transmit mode, low = receive. Should read **low**. |
| 2 | STAT | 19 (via 1 kΩ) | Output: high = linked to a phone |
| 3 | GND | | Scope/meter reference |
| 4 | MODE | 12 | Button input, active **high**: bridge 4–5 to press |
| 5 | COM | | +3.3 V through 10 kΩ |
| 6 | PP/CALL | 6 | Button input, active **high**: bridge 5–6 to press |

No shunts, ever: a shunt to GND does nothing and one to 3.3 V holds the
button down, and a 6 s hold powers the module off or re-pairs it.

## How it connects to the SMD5 main board

Both boards' netlists were checked against each other (2026-10-09). The
daughter board uses the same J1 order as the BM64 carrier, so either
plugs into the same header.

| Header pin | Main board `J2` | Daughter board `J1` → BK3266 module |
|--|--|--|
| 1 | `+3.3V_BM` from **U5** (XC6206 LDO) | → `VBAT` (pin 37) |
| 2 | GPIO17 / U0RXD (ESP receives) | ← `TX` (pin 10) |
| 3 | GPIO16 / U0TXD (ESP transmits) | → `RX` (pin 11) |
| 4 | `MFB` net, GPIO15, **R17** 100 kΩ to GND | → `WAKEUP` (pin 7) |
| 5 | **C22** 1 µF ← `Line0Vout` (SLIC) | → `MICP` (pin 30) |
| 6 | **C24** 1 µF to GND | → `MICN` (pin 29) |
| 7 | **C23** 1 µF → **R16** 1 kΩ → `Line0Vin` (SLIC) | ← `AUDIOLP` (pin 33) |
| 8 | GND | → GND, `AGND` |

- **Audio is analog.** The ESP32 never sees it; it only runs the UART and
  (optionally) WAKEUP. Line 0 is the Bluetooth line.
- **Single-ended use of a differential pair.** Only the positive leg of the
  speaker output (`AUDIOLP`) reaches the header; `AUDIOLN` floats. The mic
  input is `MICP` with `MICN` AC-grounded by C24 on the main board.
- **Header orientation matters:** pin 1 is +3.3 V and pin 8 GND, so a board
  mated 180° shorts the LDO.

### Pins the firmware uses

| Signal | Pin | Direction | Handling |
|--|--|--|--|
| UART TX/RX | GPIO16 / GPIO17 | | UART1, **9600 8N1** (the BM64 uses 115200 on the same pins) |
| WAKEUP | GPIO15 | out, rarely | Left as a plain input in normal use; only `bk_wake` drives it |

The module powers itself on at boot, so no wake handshake is needed. The
BM64's MFB sequence is *not* used.

## What the firmware does

Settings → Hardware → **Bluetooth companion module**: *Not fitted* /
*BM64 module fitted* / *BK3266 module fitted (no dial-out)*. Takes effect on
reboot (the two backends use the same UART at different speeds). Settings →
Bluetooth then turns the feature on, as before. `/api/status` carries
`bt_module` (`none`/`bm64`/`bk3266`).

| Feature | BM64 | BK3266 |
|--|--|--|
| Pair a phone from the web UI | yes | yes (`BT_CMD_MATCH`) |
| Incoming call rings the bell, lift handset answers | yes | yes (`BT_CMD_ACK`) |
| Hang up ends the call | yes | yes (`BT_CMD_NACK`) |
| Caller ID in the activity log | yes | yes (frame `0x03`) |
| Move a call placed on the phone to the handset | yes | yes (passthrough on a live call) |
| Dial out (1 + area code + number) | yes | **no** — no command for it; the dialplan stops offering it |
| EEPROM audio configuration check | yes (needed) | n/a |

The driver (`bk3266.c`) runs a task that parses frames and keeps a state
(`bk_state_t`); every 1.5 s it asks `BT_CMD_MY` for the call status, because
the protocol table has no "call ended" message. At start it queries version,
address and name, then sends `BT_CMD_RECMODE` once.

The protocol/state code (`bk3266_proto.c`) has no ESP-IDF dependency and is
tested on the Mac against the vendor's own example frames:
`firmware/test/host/run.sh` → `36 checks, 0 failed`. That proves the framing,
checksum and state mapping do what this note says — not that the module
behaves the way the documents say.

### The protocol in one screen

```
52 42 23  LEN  CMD  DATA...  CRC  23 42 52        9600 8N1
LEN = 3 + len(DATA)        CRC = (LEN + CMD + DATA...) & 0xFF
```

- **To the module:** `CMD = 0x01`, `DATA[0]` = command code.
  `52 42 23 04 01 01 06 23 42 52` = pair.
  Codes: `01` pair, `02` reconnect, `03` disconnect, `04` answer, `05`
  reject, `06` hang up, `07` redial last, `08/09` volume ±, `0A` clear
  pairings, `11` address?, `12` name?, `13` phone name?, `14` version?, `15`
  ACL?, `16` call status?, `1A` volume?, `1D` factory reset, `25` receive
  mode, `29` set name.
- **From the module:** `CMD = 0x00`, `DATA[0]` = status:
  `64` booted, `65` linked, `66/67` ACL no/yes, `68` not connected, `69` HFP
  connected (no call), `70/71/74` calling out, `72` in a call, `73`
  incoming call, `7A` disconnected. Other `CMD`s carry data: `03` caller's
  number, `02` outgoing number, `04` volume, `07` own address, `08` own name,
  `09` phone name, `0A` version.

### Console commands

All on the device's serial console (`idf.py monitor`, or the host scripts).

| Command | Does |
|--|--|
| `bk_selftest` | Parser + state mapping on built-in frames; needs no module |
| `bk_probe` | Is anything answering? Listens 2 s, sends a version query two ways, says what it saw |
| `bk_listen [ms]` | Prints raw bytes and decoded frames |
| `bk_cmd <hex> [ms]` | One command code in a proper frame (works with the driver running too) |
| `bk_frame <cmd> [data] [ms]` | Any CMD + DATA with LEN/CRC computed — for trying the other reading of the protocol |
| `bk_send <hex> [ms]` | Raw bytes, no framing |
| `bk_at <text> [ms]` | A text line + CRLF, for the text-AT firmware variant |
| `bk_state` | Decoded connection/call/name state and parser counters |
| `bk_wake [ms]` | Pulse WAKEUP (GPIO15); a short pulse is a button press |

Everything except `bk_state`/`bk_cmd` needs `bt_enable 0` first (they own
the UART). `bm64_*` commands speak the BM64 protocol and are meaningless on
this module.

## Bring-up sequence

Run `firmware/bringup/test_bk3266.py` for the guided version; this is the
manual one, with what each result means.

**Before the module is involved**
1. Mac: `firmware/test/host/run.sh` → all checks pass.
2. Main board: finish the SMD5 bring-up first ([`smd5.md`](smd5.md)). The
   daughter board needs U5's 3.3 V on J2 pin 1 — check it with the module
   *removed* (3.30 V ±2%).
3. Daughter board off the main board: continuity from J1 pins to the module
   pins in the table above (1→37, 2→10, 3→11, 4→7, 5→30, 6→29, 7→33,
   8→GND); no short between 3.3 V and GND.

**With it plugged in** (pin 1 at the 3.3 V end of J2!)
4. Power on. Measure VBAT (J1 pin 1) under load; note the current.
5. Firmware: Settings → Hardware → BK3266 → Save → reboot.
6. `bt_enable 0`, then `bk_selftest` → PASS.
7. `bk_probe`:
   - *Frames decoded* → binary-protocol firmware, carry on.
   - *Nothing at all* → check power, swap TX/RX, scope module pin 10.
   - *Printable text* → text-AT firmware; the binary driver won't work as
     is (see [open question 1](#open-questions)).
8. `bk_listen 10000` while power-cycling: a `status 0x64 ON booted` frame.
9. `bt_enable 1`; wait 8 s; `bk_state` → version, own address and name
   filled in, "last frame … ms ago" small and refreshing.
10. Probe header J2.1 (S/R) with a meter: **low** = receive mode. If it's
    high the module is in transmit mode (see open question 4).
11. Pair: web UI Settings → Bluetooth → *Start pairing*, or `bk_cmd 01`.
    The phone should see the module; `bk_state` → `connected: yes` and the
    phone's name. J2.2 (STAT) goes high.
12. Incoming call from another phone: the bell rings, `bk_state` shows
    `incoming` + caller number; lift the handset → both ends hear each
    other.
13. Hang up from either end: `bk_state` returns to `idle`. **Record what
    the module sent** (`bk_listen` during the hang-up).
14. A call placed from the phone itself, audio moved to the handset.
15. Audio: levels both ways (too hot into Vin? too quiet from the mic?),
    hiss, and whether AGND tied vs floating changes it.

## Open questions

Each is something the documents leave open; the fix named is what the
firmware already does about it, and what to look at on the bench.

| # | Question | Assumed | Settle it by |
|--|--|--|--|
| 1 | **Which firmware is on the module** — the binary "SR" protocol or the text AT one (`BT+CA`, `COM+…`)? Listings say "SR" but vendors flash either. | Binary | `bk_probe`. If text: needs a second driver, and the text firmware's unsolicited events are undocumented |
| 2 | **Does a command go out as CMD `0x01` + code in DATA**, or with the code as CMD? The spreadsheet's worked examples show the former; the research note read the latter. | CMD `0x01` | `bk_probe` tries both and shows which one gets a reply |
| 3 | **What announces a call ending?** The status table has none. | Poll `BT_CMD_MY` every 1.5 s; `0x69` = idle | Hang up during `bk_listen` and read the frames |
| 4 | **Does it boot in transmit mode?** The manual's wording is garbled. | `BT_CMD_RECMODE` once after the first reply | S/R pin (J2.1) before and after; does `0x25` survive a power cycle? |
| 5 | **Are `0x70`, `0x71` and `0x74` all "calling out"?** The sheets disagree on the labels. | All three = outgoing | Place a call from the phone and watch which arrives |
| 6 | **Own address format:** 6 raw bytes or ASCII? | Either (parser handles both) | `bk_state` after boot |
| 7 | **Is 3.3 V enough?** The module manual says VBAT 3.3–4.2 V; the chip datasheet 2.8–4.2 V. U5 gives 3.3 V ±2%, so it sits at the module's stated minimum. | Fine | Watch `bk_state` for resets, and scope VBAT during a Bluetooth TX burst |
| 8 | **WAKEUP semantics:** the schematic says a short press = disconnect/reconnect; the manual says power on. | Never touch it | `bk_wake 300` with a phone connected |
| 9 | **Output level and DC bias** of `AUDIOLP` into `Line0Vin` (through 1 µF + 1 kΩ). The DAC is rated 1.1 Vrms differential; one leg is about half. | Fine | Scope J1.7 on a call with loud speech |
| 10 | **Does the module need a "single-ended output" setting?** The text firmware has `COM+DACSINGLE`; the binary protocol has no such command. | No | Listen for distortion/low level; compare with `AUDIOLN` jumpered |
| 11 | **Dial-out.** The firmware has action codes up to `0x1C` that look like "send DTMF digit 0–9" (`0x13`–`0x1C`) and `0x0B` voice dial. | Not used | `bk_frame 01 13` during an active call; if a tone goes out it opens DTMF-over-call, not dialing |
| 12 | **Name:** `BT_CMD_BT_NAME` (`0x29`) takes the name as DATA. The driver doesn't send it yet, so the module advertises its own default name. | Default name | `bk_frame 01 "29 …name bytes…"` and see what the phone shows |
