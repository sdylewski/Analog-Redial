# Contributing to Analog Redial

Thanks for wanting to help. This is a small hobby project run by one person, so
contributions of every size are welcome: a bug report, a typo fix, a note that
"this step in the build guide confused me", or a whole feature.

## Talk to us

- **Questions, show-and-tell, build help:** [Discord](https://discord.gg/zEZkqfcxqE)
- **Bugs and feature requests:** [GitHub Issues](https://github.com/sdylewski/Analog-Redial/issues)
- **Not sure whether something is a bug?** Ask first. It's fine to be wrong.

## Safety first

This board connects to real telephone wiring that carries **about 48 V DC**
off-hook and **about 60 V AC** while ringing. It is **not** approved for
connection to a public telephone network (the phone company's line), only to
phones you plug into the board itself. Please don't touch the RJ12 pins while
the board is powered, and don't send us layout changes that shrink the
tip/ring spacing described in the [SMD4 hardware reference](docs/hardware-smd4.md).
Hardware changes get a closer look than firmware changes for this reason.

## Where help is most useful

- **Testing on real phones.** Different rotary dials, touch-tone handsets,
  and ringers behave differently. "It works on my Western Electric 500" or "the
  ring is too weak on my Trimline" is valuable.
- **VoIP servers.** Reports from Asterisk, FreePBX, and commercial SIP
  providers: what worked, what needed a setting.
- **Home Assistant.** The MQTT integration has not been verified against many
  setups yet. Tell us what you see.
- **Documentation.** If a step was unclear, wrong, or missing, that is a bug.
- **Translations** of the web interface.
- **Cases and mounting.** 3D-printable enclosures for the current board.
- **Which board to build:** build the **v5** board. v6 is in progress and
  untested; hardware feedback on it is welcome but expect rough edges.

## Building and testing the firmware

The firmware is plain ESP-IDF C. The full toolchain setup is in
[docs/flashing.md](docs/flashing.md) and [firmware/README.md](firmware/README.md).
The short version:

- Use **ESP-IDF v5.2.8** exactly. The tracked `sdkconfig` is generated by it.
- The default `build/` directory targets the current board (SMD4/SMD5 pin map).
- For any other board type, use a separate build directory **and pass an
  explicit `-D SDKCONFIG=...`**, otherwise `idf.py` can silently modify the
  shared `firmware/sdkconfig`:

  ```bash
  idf.py -B build.smd2 -D SDKCONFIG="build.smd2/sdkconfig" \
    -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.smd2.defaults" \
    set-target esp32c6
  ```

- Always check `git status firmware/sdkconfig` before committing. A modified
  `sdkconfig` after a build usually means a version mismatch or the wrong build
  directory, not something to commit.
- Hardware-independent logic (DTMF detection, protocol parsers) has host-side
  tests: `firmware/test/host/run.sh`. Please run them if you touch those parts.
- Memory is tight on the ESP32-C6. Avoid large contiguous allocations (stream
  in small chunks instead) and check free heap if you add a feature that runs
  during a call.

## Making a change

1. Fork the repo and make a branch.
2. Keep each pull request focused on one thing. Small is easier to review.
3. Match the style of the surrounding code (naming, comments, formatting).
4. Say how you tested it: which board, which phone, what you did. "Builds
   cleanly" and "tested on hardware" are different, and both are useful to
   know.
5. Update the docs if behavior changes. The public docs (`README.md` and
   `docs/`) describe the board as it is today; they are not a changelog.
6. Open a pull request with a short description of what and why.

Commit messages: a short summary line, then a paragraph on the reason if it is
not obvious.

## Never commit secrets

Before you push, check your diff for Wi-Fi passwords, web or setup passwords,
SIP/VoIP credentials, VoIP enrollment keys, API tokens, and your own network
names or IP addresses. If you accidentally push one, **change it first**, then
tell us; deleting the commit does not make a leaked secret safe.

## Hardware changes

KiCad files live under `hardware/kicad/`. If you propose a change:

- Run the design-rule check and include the result.
- Explain what problem it fixes, and keep the tip/ring clearances
  (0.8 mm target) intact.
- Don't expect it to be merged until someone has built it.
